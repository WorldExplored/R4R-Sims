## Representation/import feasibility

1. **Calibrated real photos + poses directly:** no inspected RflySim loader accepts this as reconstruction input. Camera parameter fields configure simulated sensors; they are not a photogrammetry pipeline. Missing imagery/calibration/split blocks this R4R stage.
2. **Existing reconstruction mesh:** official `3d-import.html` says FBX/OBJ enter the UE editor, are baked/packaged, copied into project/plugin Content and indexed by XML `ModelType`, `MeshPath`, `Scale`. It resolves cooked `/Game/` and `/Rfly3DSimPlugin/` assets, not arbitrary OBJ/PLY at runtime. This is a documented conversion route; actual packaged loader implementation and **Free Edition eligibility for the selected outdoor map/import workflow remain unverified**. Do not introduce an engine build as a workaround. Global origin, NED/UE axes, centimetres/metres and reconstructed scale need surveyed anchors.
3. **Gaussian representation:** no supported Gaussian-splat loader found in the official installation, import, sensor documentation or inspected camera source. Gaussian noise fields do not mean Gaussian splats. A custom UE plugin/cooking path or external renderer adapter would be required; neither is established or implemented here.
4. **Replacing UE:** infer a possible separate process consuming truth, calculating calibrated camera pose and providing images to an external consumer. This is distinct from (a) exporting a pose route, (b) replacing native RflySim3D, and (c) feeding a closed-loop visual controller. Image ownership, timestamps, reset/step, collision/depth services, licensed/closed engine boundary and policy adapter are unresolved. Keep UE collision proxies or a separately validated geometry service if replacing visual radiance. A Gaussian field alone does not establish contact geometry or depth fidelity.

## Applicability and learning guide

Indoor: documented sensors/control may support integration; occlusion, metric geometry and visual navigation performance not tested. Residential/campus/suburban outdoors below 100 m: imported cooked meshes are a candidate baseline, while capture/reconstruction/fidelity remain blocked. Sparse captures require held-out views at horizontal/vertical baselines; sparse scene content requires task-specific perception tests. Racing: stock route is insufficient for gate detection, high-speed dynamics/control/collision timing. PX4/MAVLink is relevant to real companion-computer control, but real transfer needs dynamics, sensors and latency calibration; HITL remains outside scope.

Read installed `SITLRun.bat` and PX4 firmware parameters to identify process/port/control ownership; `PX4MavCtrlV4.py` for NED, timestamp and offboard keepalive; `VisionCaptureApi.py` for camera handshake/mmap/locks/clock fallback; `UE4CtrlAPI.py` CameraData/crash methods for actual poses and contacts; scene XML/mesh metadata for scale and origin. CopterSim advances motion, PX4 estimates/stabilizes, UE renders/queries geometry, Python supplies setpoints. MATLAB/Simulink authors models; precompiled stock models may avoid it. SITL uses software PX4; HITL uses a physical flight controller and is a different experiment.
