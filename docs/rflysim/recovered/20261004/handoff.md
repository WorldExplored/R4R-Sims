# RflySim phase 1 handoff — 2026-10-04

**Status:** source/documentation investigation and a locally syntax-checked runner; **no RflySim binary, PX4, GPU run, camera frame, or flight result executed**. This candidate is independent of other simulator audits. Real4Real (R4R) here means Air Labs' real-drone research, not the R2R navigation benchmark.

## Reproduction chosen

Use the current **RflySim Toolchain Free Edition**, one stock quadcopter, stock RflySim3D UE4 scene, PX4 SITL, and the installed RflySimSDK Python interface. This is a level **B** experiment: position setpoints lead to PX4/CopterSim state observations, with UE camera frames if the included RGB sensor configuration works. Level **A** is the optional camera capture over a known vehicle/camera route in that native scene. Level **C** is **unavailable**: no released pretrained navigation/racing policy or weights were identified, and the scripted waypoint controller is not a learned policy. Do not train or substitute random weights.

```
reference NED setpoints -> RflySimSDK PX4MavCtrler -> MAVLink/PX4 SITL
 -> actuator outputs -> CopterSim vehicle DLL/sensors -> PX4 estimates
 -> actual state record + vehicle pose to RflySim3D (UE4)
 -> UE visual sensor -> VisionCaptureApi -> timestamped frames
```

CopterSim handles the motion model; PX4 handles low-level stabilization and modes; RflySim3D handles rendering, collision, and visual sensors. MATLAB/Simulink is the authoring/compilation route for changed dynamics/firmware models, not necessary to try the released precompiled model via the fast installer. MATLAB Runtime may be pulled by the installer; verify the actual build. Licensed MATLAB/Simulink and toolboxes are needed if modifying/compiling models. Ubuntu/WSL hosts PX4/ROS/algorithms; the documented visual program and installer run on Windows. SSH can move files and run headless scripts after preparation, while mounting ISO, installer prompts, WSL enabling/reboot, RflySim3D graphics session, and sensor configuration need an interactive Windows desktop. Do not disable security software merely because an install guide suggests it.

## Interfaces and trajectories

The control algorithm is a deterministic timed local-position waypoint sequence using `initOffboard`, `SendPosNED`, `SendMavArm`, then `sendMavLand`. Inputs: reference NED position (metres), yaw (radians), and the SDK's PX4 estimates. Outputs: actions/setpoints, PX4 estimated position, velocity/attitude if exposed, CopterSim true state if exposed, and UE RGB frames if configured. The runner does not infer that state estimates equal truth. Verify firmware, parameters, vehicle DLL, UDP/MAVLink ports, arming mode, and command acknowledgments on host. The stock test route is origin -> NED `(0,0,-2)` hover -> `(2,0,-2)` -> `(2,2,-2)` -> `(0,0,-2)` -> land, each segment bounded; a collision-free scene and operator approval are required before arming. Separate `reference_route.json`, `actions.jsonl`, `vehicle_state.jsonl`, `camera_poses.jsonl` and `frames/`. Actual vehicle path and camera extrinsics must not be reconstructed from reference setpoints. If a camera pose API is unavailable, `camera_poses.jsonl` records missing values and frames are not used as geometric ground truth.

The native stock scene/vehicle is a **sanity reproduction**, not an indoor/outdoor/racing result. Later common-scene/common-camera-route work needs a metrically scaled, licensed scene, calibrated camera, fixed intrinsics/extrinsics, identical route, and matching exposure/resolution. For outdoors, especially sparse terrain, assess coverage gaps, visibility and novel views; no current demo establishes reconstruction fidelity. Racing requires a gate course, speed/control limits and collision truth, all absent from this first test.

## Gaussian replacement assessment

RflySim already separates dynamics/PX4 state traffic from UE visuals at a network/API boundary. A custom Gaussian renderer could subscribe to actual body pose, apply calibrated body-to-camera extrinsics and return RGB along the same capture boundary; that is **an engineering hypothesis**, not a supported drop-in integration. RflySim3D also supplies collision queries and depth/other visual sensors, so removing UE may remove physics-relevant scene contact and perception modalities. Test separately whether CopterSim's ground/collision model handles the chosen scene, and whether a custom renderer can deliver images with bounded latency, timestamps and camera calibration to the policy process. A Gaussian radiance field alone gives no reliable collision geometry, physical material model, or guaranteed sparse/outdoor novel-view coverage. Keep a mesh/SDF or other collision model if needed. First compare the same camera route and source assets, then close the loop; measure image quality, latency, geometry consistency, and navigation outcomes separately. Do not claim real-world transfer from stock SITL.

## R4R use cases and learning guide

**Indoor navigation:** plausible camera and PX4 integration test; stock scene lacks task annotations and calibrated real-camera matching. **Outdoor/sparse navigation:** useful interface experiment; source reconstruction, long-range parallax, sparse views, lighting and GNSS conditions require new evidence. **Racing:** useful control timing/trajectory harness; stock hover route cannot establish gate perception or high-speed dynamics. **Real drone relevance:** PX4/MAVLink and companion-computer interfaces can be carried toward HITL and flight, but model, sensor, latency and safety calibration remain to be measured. HITL with a physical autopilot is a later distinct experiment.

Read, in order: installed `SITLRun.bat` (processes/ports), `PX4MavCtrlV4.py` (`initOffboard`, `SendPosNED`, NED/time fields), `VisionCaptureApi.py` (`jsonLoad`, `sendReqToUE4`, `startImgCap`, `Img`), `Config.json` (intrinsics, mount pose, frame IDs), CopterSim model config/DLL manifest (dynamics), PX4 firmware version/parameter export, and this audit's `run.py`. Learn NED vs UE axes and metres vs UE centimetres before comparing poses. Learn PX4 offboard keepalive/failsafe, arming/landing, SITL vs HITL, and wall vs simulation clocks. A supervisor should be able to trace each image back to a timestamped actual pose and each actual pose back to PX4/CopterSim state, not to a commanded waypoint.
